# 计费（用户侧）

用户真的付钱，所以这里有两套数：**成本**（我们付给供应商的，单位元）和**积分**
（用户看到的，单位"分"）。成本只在内部可见，**任何面向用户的接口都不返回它**。

定价公式（产品口径）：

```text
积分 = 成本（元） × 倍率 × 100
```

所以 1 积分 = 0.01 元（在用户侧），倍率已经折进积分数量里。成本 1 元、倍率 2 →
用户看到 200 积分（= 付 2 元）。

## 两套账本

| | 存哪 | 谁看 | 内容 |
| --- | --- | --- | --- |
| 成本台账 | `backend/data/<project>/usage.json` | 运营 / 排障 | 每次调用的成本（元）、原始 usage、缺价标记 |
| 用户账本 | `backend/data/billing.sqlite3` | 用户 / 计费 | 每次调用的积分，从余额扣 |

两份都由 `services/usage_service.record()` 写：它先落成本，再调 `billing.service.charge()`
落用户价。**成本价格表在两处各有一份**（`usage_service._PRICE_TABLE` 与
`billing.pricing.COST_TABLE`），`test_billing.py` 断言两边完全相等——不一致会让"成本"
和"对外定价"漂开。

## 口径

- 币种只有 **CNY**（北京站），不支持国际站。
- **不考虑 DeepSeek 峰谷价差**：统一按峰时价一条线，账本里不记时段。
- **没有免费额度**：所有用量都计价。缺价时记 `no_price`（0 元、不扣钱），但要能被运营看见
  （`project_summary()["unpriced_calls"]` 只出现在内部视角）。
- 两种整数：成本用 **micro 元**（1e-6 元），积分用 **micro 积分**（1e-6 积分）。
  单句常常不到 1 积分（¥0.0006 → 0.12 积分），用整数存才不会在累加时丢零头。
  接口同时给 `*_micro` 和 `*_points`（已换算好的显示值）。
- 本地配音（Kokoro）、人声分离、ffmpeg 导出**不消耗积分**，账本里记 0 + `cost_source=free`，
  这样用户看到"这个工程没消耗"时能对上号。

## 倍率

`config.BILLING_MARKUP`：按步骤配（`tts` / `asr` / `omni` / `llm` / `clone`），
默认 2.0，可用环境变量覆盖：

```dotenv
BILLING_MARKUP_TTS=2.0
BILLING_MARKUP_ASR=2.0
BILLING_MARKUP_OMNI=2.0
BILLING_MARKUP_LLM=2.0
BILLING_MARKUP_CLONE=2.0
```

每笔账都存下当时的 `markup` 与金额快照，**改倍率不改历史**。倍率只影响之后的价格。

## 新用户赠送

首次创建账号（不是每次登录）送 `BILLING_SIGNUP_BONUS_POINTS`，默认 **500 积分**
（≈ ¥5）。设为 0 即关闭。

- 幂等靠 `adjustment.id = "signup:<user_id>"` 固定主键 + `INSERT OR IGNORE`：
  并发首次登录也只会发一次；不需要额外查重。
- 只发给**之后新注册**的账号；上线前已存在的账号不补发。
- 发放失败不影响登录（送积分是附加动作，只记日志）。

## 视频时长限制

`MAX_DURATION_SECONDS`（默认 30 分钟），上传时 ffprobe 探一次，超了直接 413，不建工程。
前端选完文件后用 `<video preload=metadata>` 在本地也探一次，不等上传完就禁用「开始」并说明超长。
时长写进 `VideoState.duration`，估算、限制、展示都读它。

## 初始化费用估算（替代固定起步门槛）

`billing/estimate.py`：按时长 + 设置估一次初始化要花多少积分（**上界**）。每个系数都对应
一个**独立的计费口径**，不再按"每句多少 token"一把估：

| 步骤 | 计费口径 | 30 分钟 ≈ |
| --- | --- | --- |
| LLM 翻译 | 按分块（每块 1500 入）+ 术语表；输出按**关 thinking**（300/块） | 130 |
| TTS | 按调用：每次输出 ≈ 45 token，每句 1.4 次；官方实测 ¥0.0095/分钟音频 | 77 |
| omni 审听 | **整段音频一次调用**，音频 ≈ 6 token/秒 + prompt 1000 | 11 |
| ASR | 按 token，≈ 时长 | 7 |
| 克隆 | 每说话人 2 积分 × 3 | 6 |
| **合计** | | **≈ 231 积分（¥2.3）** |

10 分钟 ≈ 82，34 秒 ≈ 12。

**关 thinking 是最大的一项优化**（`LLM_REASONING_EFFORT=none`，默认）：实测同一段译文
`none` 输出 36 token / `low` 输出 ~300（含推理块）。翻译不需要显式推理链。

质量验证（真实 9 句，用项目自己的翻译函数 A/B）：none 与 low 的译文各有胜负、整体无差；
真正的问题在别处——**prompt 里原本一个字没提情感标签**，两种模式都把 `[curious]` 当正文丢掉
（标签丢了 = 那句在成片里没了情绪）。已加第 7 条规则要求原样保留，并在后处理里把漏掉的补回句首。

**为什么 omni 比 LLM 便宜**（同样处理 9 句：翻译 ¥0.014，审听 ¥0.0018）：deepseek-flash 输出
单价 ¥8/百万是 omni（¥2.7）的 3 倍；而且审听从一开始就 `enable_thinking=False`，输出只有 331 token，
翻译当时开着推理输出 1419。两件事叠起来 8 倍。

**omni 审听本身很便宜**，不需要优化：它一次调用听完整个视频，音频 token 只 6/秒。
之前以为贵，是把 chat 轮次和克隆选材混进来了。

用到它的三个地方：
- **落地页**：选完文件本地探时长 → `POST /api/billing/estimate` 按当前设置算 → 「开始」按钮上显示
  `约 N 积分 · 余额 M`；余额不够时按钮禁用并写明差多少
- **setup**：服务端用**这次**的设置再算一次，余额不够返回 **402**（不是跑完 ASR/翻译才拦）
- **`_need_balance`**：`run_initialize` 等命令的起步门槛改为按工程时长估；没有时长的老工程退回
  `BILLING_MIN_START_POINTS_MICRO`（100）

`test_billing.py` ⑦ 守住"34 秒估算 ≥ 40.4 且 < 1.5×"这条校准，系数改坏会被发现。

## 余额与拦截

- 预付费积分，管理员/线下充值到账后调用 `POST /api/billing/adjust`（入参 `amount_points`）。
- 会花钱的命令（`redub` / `retranslate` / `clone_voice` / `generate_voice_candidates` /
  `run_initialize`）在动手前检查余额，不够就拒绝并说清差多少。
  门槛是 `BILLING_MIN_START_POINTS_MICRO`（默认 100 积分，约 ¥1 的量级）——按用量计费没法精确预估，
  这个数只是"别让余额见底的人开跑十分钟的活"。
- **扣积分发生在每次调用之后**（按实际用量）。所以一个任务跑完可能把余额扣成负数：
  活已经干完，不能事后拒付；下一次任务会被拦住。
- 充值/扣减写 `adjustment` 表，和账本一起构成"余额为什么是这个数"的完整解释。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/billing/summary` | 余额、本月已用、按步骤 |
| GET | `/api/billing/entries?limit=&project=` | 明细（不含成本） |
| GET | `/api/billing/prices` | 用户可见单价（已含倍率；目前只有克隆） |
| GET | `/api/billing/projects/{id}` | 单个工程累计（自己的工程，别人的 404） |
| POST | `/api/billing/adjust` | 管理员调整余额（`BILLING_ADMIN_EMAILS`） |

命令层（UI 和 AI 共用）：

- `get_cost`：这个工程花了多少（用户价）。
- `get_billing`：账户视角（余额 / 本月 / 按步骤），可附最近明细。
- `get_price`：某项服务的单价（目前只有 `clone`）。

## 前端

- **首页右上角**：`◎ 837.87` 药丸（`components/billing/CreditsPill.tsx`），点开是玻璃浮层：
  `积分 / 837.87 可用` + 本月消耗条 + `本月已用 x · n 次` + 全宽「充值」+「费用明细 ›」。
  进度条表示"本月消耗占（本月消耗 + 余额）的比例"，不是虚构的月额度。
- **费用明细**（`BillingPanel.tsx`）：表格式，四列 时间 / 项目 / 说明 / 积分，顶部是余额摘要
  （在工程页多一行"本工程累计"）。明细保留 2 位小数、去掉尾随 0。
- **编辑页顶栏**：`本工程 162.13 积分` 胶囊，悬停或点击展开小卡：按步骤拆分 + 余额 + 「明细」。
  顶栏是 `overflow-hidden`，所以卡片用 `fixed` 定位（`absolute` 会被裁掉）。
- **账户菜单**：只留一个「费用明细」入口（余额已由首页药丸承担）。
- **确认卡**：能算准的给预估（克隆 2 积分 × 次数），算不准的明说"按实际用量计费"。
- **音色面板**：单价从 `/api/billing/prices` 取（单位积分），不再写死在代码里。
- **充值**：在线支付未接，点「充值」目前只提示"联系管理员"。

## 已知边界

- 账本是**估算级**：供应商控制台的优惠、免额、峰谷价都不在账本里。真实账单以阿里云为准。
  对账（拉账单 API 比对）还没做。
- 多标签页/多设备同时用一个账号：余额扣减是 SQLite 事务，不会丢账，但"余额刚够"时
  两个任务可能都通过预检、最终把余额花成负数——和单任务透支同一个处理方式。
- 历史工程（计费上线前的花费）**不迁移**进用户账本：那时没有积分口径，补记等于凭空造欠账。
- 旧的"元计价"账本结构（`price_micro`/`balance_micro` 列）在启动时会被识别并**重建**：
  计费还没上线，没有需要保留的换算依据。
